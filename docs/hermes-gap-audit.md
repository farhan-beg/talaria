## 1. What the gateway offers

The transport is WebSocket JSON-RPC 2.0 at `/api/ws` (one JSON object per line).
- Events arrive as `{"jsonrpc":"2.0","method":"event","params":{"type":<event>,"session_id":<runtime sid>,"payload":{...}}}`.
- Server→client requests arrive as JSON-RPC requests with an `id`. You answer with a JSON-RPC response, or with `request.answer {id, result}` if the original frame was lost.
- Most methods accept an optional `profile` (`ProfileParams`). That is how one gateway serves several profiles.

## 2. Prioritized gaps

### P0: broken or wrong today

**1. Fast mode resets after a reply (root cause found).**

Contract facts:
- `config.set {session_id, key:"fast", value:"fast"|"normal"|"ultrafast"|"auto"|"cold"|"on"|"off"|"toggle"|"status"}` is **session-scoped** (`_SESSION_SCOPED_KEYS = {model, fast, yolo, reasoning}`, `tui_gateway/methods_config_set.py`).
  - With a live agent it sets `agent.service_tier` (`"priority"` for fast, `None` for normal) and `request_overrides`, persists `model_config.service_tier` on the stored row, and emits `session.info`.
  - **Before the agent is built** it only stores a pin, `session["create_service_tier_override"]` (`"priority"`, or `""` for normal).
  - With no `session_id` it writes the global default `agent.service_tier` to config.yaml. That affects every surface and every new session.
  - The result is `{key, value:"fast"|"normal"|...}`. It errors with code 4002 and "fast mode is not available for this model" when the route has no fast tier.
- `config.get {session_id, key:"fast"}` returns `{value:"fast"|"ultrafast"|"normal"}`. It reads the live agent's tier, else the pin, else global.
- `session.info` (also returned as `info` by create/resume/activate) carries:
  - `service_tier`: the raw tier, `"priority"`, `"ultrafast"`, `"auto"`, `"cold"` or `""`.
  - `fast`: a bool. **True only if the tier is static (priority/ultrafast) AND the current route actually honours it** (`_fast_tier_applies`, `server.py:2393`).
- `session.create` accepts `fast: bool` (true pins priority, false pins normal, omitted inherits the profile default) and `service_tier: "ultrafast"|...` (`methods_session_model_guard.create_overrides`). `session.resume` has **no** fast param.

The race that causes the reset:
- `session.create` returns before the agent builds ("agent builds after the reply"). Cold `session.resume` calls `_schedule_agent_build` right after replying (`methods_session.py:_resume_cold`).
- The build reads its kwargs once (`server.py:1030-1040`). For a resumed chat with stored runtime it uses `resume_runtime_overrides` and **ignores `create_service_tier_override` entirely**.
- So a `config.set fast` that lands while the agent is unbuilt or mid-build only sets the pin. The agent comes up with the stored or global tier.
- After the build, `session.info` arrives with the real model. ChatScreen's `LaunchedEffect(conn, model)` then reruns `loadRunSettings()`, and `config.get fast` now reads the agent and answers `"normal"`, so the toggle flips off.
- The WS orphan reap makes it worse. A detached session is reaped after **20 s** (`ws_orphan_reap_grace_s`), so every time Android backgrounds the app past that, the next `session.resume` rebuilds the agent again.

The correct persistent mechanism, matching the desktop:
- **New chat:** send the preference atomically, as `session.create {..., fast: true}` (or `fast: true, service_tier: "ultrafast"`). If an old backend rejects `service_tier` with "invalid params for session.create: service_tier:", resend without it. The desktop does exactly this (`apps/desktop/src/app/session/hooks/use-session-actions/index.ts:395-398`, `session-create-request.ts`).
- **Resumed chat:**
  - Option (a): resume with `eager_build: true` so the agent exists in the response, then call `config.set {session_id, key:"fast", value:"fast"}`.
  - Option (b): wait until the first `session.info` after resume that has a non-empty `model` and no `lazy`, then call `config.set`. Re-assert only when `info.service_tier` is not in `{"priority","ultrafast"}`.
- **Where the preference lives:** the desktop keeps a client-side per-model preset keyed `provider::model` (`store/model-presets.ts`) and re-applies it with `config.set key:"fast"` when the model is selected. A global Android pref is fine, but key it per model if you want desktop parity.
- **Global default:** the desktop Settings → Model "Speed" control writes `agent.service_tier` via REST `PUT /api/config` (or `config.set {key:"fast", value}` with no session_id). New sessions with `fast` omitted inherit it. Use this for an "always fast" setting instead of re-applying on every chat.
- **What the toggle should show:** preference = `service_tier ∈ {priority, ultrafast}`; effective = `info.fast`. Show "not applied on this route" when the preference is on but `fast` is false. Today `fastFromInfo` treats `service_tier` alone as truth.
- **Stop the read-back race:** don't call `config.get fast` from `LaunchedEffect(model)`. Trust the `session.info` frames, which are emitted after every successful `config.set` on a built agent.

State of the concurrent edit: `loadRunSettings()` now re-asserts `config.set fast` when `store.fastPref` is set. That still hits the pre-build race on resume and still never passes `fast` on `session.create`.

**2. Missing `profile` on session RPCs for non-default profiles.**
- `session.resume`, `session.history`, `message.react`, `config.*`, `commands.catalog` and the others accept `profile`. `session.resume` uses it to find the row in that profile's state.db (`_Resume.profile`).
- Android passes `profile` only on `session.create`, `commands.catalog`, `complete.slash` and `complete.path`. Resuming a chat from a non-default profile can fail with 4001 or resolve against the wrong store.
- Fix: send `profile: store.profile` on every session and profile-scoped call.

**3. Reconnect loses in-flight state.**
- `session.resume` and `session.activate` return:
  - `running`, `turn_started_at`
  - `inflight {user, assistant, streaming, status, error, ...}` (the partial reply so far)
  - `queued {user}`
  - `pending_approval {request_id, command, description, choices, allow_permanent, allow_session, ...}`
  - `open_requests [{id, method, params}]`
  - `todo_state {todos, revision}`
  - `auto_continue`
- Android uses only `messages` and `info.running`.
- Missing pieces:
  - Seed the streaming bubble from `inflight.assistant`.
  - Turn each `open_requests` entry into a `ServerAsk` and answer it with `request.answer {id, result}`.
  - Show `pending_approval` and answer with `approval.respond {session_id, choice:"once"|"session"|"always"|"deny", all?, request_id}`.
  - Call `approval.received {session_id, request_id}` when the card renders. This starts the server's timeout clock.
- Optional gap-free replay: `gateway.ready.replay_epoch` plus `session.events.since {session_id, last_seen}` → `{events, latest_seq, truncated, epoch, open_requests}`. On `truncated` or an epoch change, fall back to resume.

**4. Reasoning is missing on non-streaming providers.** Handle `reasoning.available {text}` (a whole block) and `message.complete.reasoning`. Today only `reasoning.delta` and `thinking.delta` are handled.

**5. `approval.cancelled`, `session.reclaimed` and `message.complete.error_surface` are not handled.**
- `approval.cancelled {request_ids[], reason}`: remove those approval cards (the backend resolved them as deny).
- `session.reclaimed {session_id, stored_session_id, reason}`: the runtime sid is dead, so resume `stored_session_id`.
- `message.complete.error_surface {layer, code, retryable, provider, model, resets_at}`: use it for a "Retry"/"rate-limited until" UI. Also `recoverable` and `partial`.

### P1: features the desktop exposes and Android lacks

**6. Message reactions: spec, and where the in-progress code stands.**
- **Set or clear:** `message.react {session_id (live runtime sid), row_id?: int, newest_role?: "user"|"assistant", emoji?: string|null, author?: "user"|"agent" (default "user"), profile?}` → `{row_id, reactions: [{emoji, author, at?, seen?}]}`.
  - Tapback semantics: one reaction per author; the same emoji again or `null` clears it.
  - Errors: 4023 if neither row_id nor newest_role; 4024 for an empty emoji; 4025 for a bad author; 4040 "no message to react to yet" / "message not found in this session"; 5007 DB.
  - The server resolves the row against `_submit_row_target_key(session)`, so it survives a compression rotation.
- **Live agent reaction:** `message.reaction {row_id, reactions[], role}`. Paint it only for the active session. If the row id is unknown, apply it to the newest message of `role` and learn the id.
- **History:**
  - Reactions live in **`display_metadata.reactions`** on each `TranscriptMessage`. `display_metadata` may be a JSON **string**, so parse it (the desktop does: `lib/chat-messages/hydration.ts:179-235`).
  - `row_id` is present in `session.resume`, `session.create` and `session.history` messages (all read with `include_row_ids=True`). REST `/api/sessions/{id}/messages` also carries them.
  - There is no separate `include_row_ids` RPC param; it is always on for the gateway projections.
- **Row ids for live turns, without text matching:**
  - `prompt.submit` → `user_row_id`.
  - `message.complete.persisted_turn = {row_ids[], complete, user_row_id?, final_assistant_row_id?}`. Use `final_assistant_row_id` to stamp the reply. Fall back to `newest_role` (what the desktop does in `store/reactions.ts`).
  - The in-progress `syncRowIds()` matches `session.history` text and should be replaced with this.
- **Agent awareness and gating:**
  - User reactions are fed to the model on the next turn only if config `display.message_reactions` is true (`methods_prompt._pending_reaction_notes`). Turn it on with `config.set {key:"display.message_reactions", value:true}`. This is a global display toggle; the desktop mirrors its own Appearance switch onto it.
  - The agent's own `react_to_message` tool is in the `desktop_ui` toolset, which is folded in only for sessions whose **source == "desktop"** (`server._gui_surface_toolsets`), and also needs `display.message_reactions`.
  - So on Android sessions the agent will not react back unless the session is created with `source:"desktop"`. **Don't do that:** it would also expose desktop-only tools (preview, pane, terminal.read, window.read, tour) that Android can't serve. Render agent reactions when they appear (from desktop-originated sessions or history).
  - The desktop's quick set is `['❤️','👍','👎','😂','‼️','❓']`.
- **The separate `reaction {kind}` event** is an "affection detected in the user's message" signal (hearts etc.), not a tapback. Optional, purely decorative.

**7. @-mentions and file references in the composer.**
- `complete.path {word, session_id?, cwd?, profile?}` → `{items: [{text, display, meta, kind?}]}`. Show `display`, insert `text`.
  - Send `word` **including the leading `@`**.
  - Bare `@` → directive hints `@diff`, `@staged`, `@file:`, `@folder:`, `@url:`, `@git:`, plus `@<profile>` agent mentions, plus plugin `@<prefix>:` providers.
  - `@name` (2+ chars) → fuzzy basename search over the repo, folders first, max 30. Item text is `@file:<rel>` or `@folder:<rel>/`.
  - `@file:`, `@folder:` or a path containing `/` → directory listing. Selecting a folder should immediately re-query to drill in.
  - `@<prefix>:<q>` → plugin completions.
- The desktop sends `word = REF_STARTERS.has(q) ? "@"+q+":" : "@"+q` and caches per `cwd|sessionId|query` (`apps/desktop/src/app/chat/composer/hooks/use-at-completions.ts`).
- Expansion is server-side at `prompt.submit` (`agent/context_references`), so the client just keeps the `@file:path` text.
- `@<profile>` mentions route to another profile in multi-agent UIs.
- State of the concurrent edit: Android now calls `complete.path` with the current token. Check that it keeps the `@`, re-queries after a folder pick, and caches.
- **Related:** `file.attach` returns `ref_text`/`ref_path`. Insert `ref_text` (the `@file:` ref) into the prompt, which Android already does.
- Also `paste.collapse {text}` → `{placeholder, path, lines}` turns a huge paste into a file ref.

**8. Session list filters.**
- REST `GET /api/sessions?limit&offset&order=recent|created&archived=exclude|only|include&min_messages&source=&sources=a,b&exclude_sources=a,b&cwd_prefix&profile&full`. The row has `id, source, title, preview, started_at, last_active, message_count, archived, pinned, is_active, profile, ...`.
- Desktop recents use `exclude_sources = acp,cron,kanban,oneshot,subagent,tool,<every messaging platform>` with `min_messages=1` (`use-session-list-actions.ts:66-78`). Cron gets its own slice via `source=cron`; messaging platforms get theirs via `exclude_sources=cron,acp,cli,codex,desktop,gateway,kanban,local,oneshot,tui`.
- **How subagents behave:** delegate children are hidden by default (`include_subagents=False`) unless the profile config has `sessions.show_subagents: true`. Even then they appear only if the list has no source scope and either no exclusions or an exclusion list that **includes** `subagent` (`hermes_cli/session_listing.subagent_listing_scope`).
- So Android's `HIDDEN_SOURCES = cron,kanban,tool,recovered`, which deliberately omits `subagent`, does keep children hidden. But it misses **`acp` and `oneshot`** and lets messaging-platform threads interleave with chats.
- Recommended chats list: `exclude_sources=acp,cron,kanban,oneshot,tool,recovered` (add `subagent` only if you want the server's `show_subagents` to apply) plus `min_messages=1`.
- Batched alternative: `GET /api/profiles/sessions/sidebar?recents_profile=<name|all>&recents_limit&recents_exclude=...&cron_limit&messaging_limit&messaging_exclude=...` → `{recents, cron, messaging: {sessions, profiles_truncated, ...}, storage}`.
- **Hide, archive, pin, unread:** `PATCH /api/sessions/{id} {title?, archived?, hidden?, pinned?, unread?, profile?}`, or the RPCs `session.archive {session_id|session_key, archived}` and `session.set_hidden {session_id, hidden}`. Hidden and archived rows leave the default list; `archived=only` lists the archive. `pinned` exempts a row from auto-archive.
- RPC `session.list {limit?, title?, include_hidden?}` already denies sub-agent and kanban sources.
- Refresh the list on the **`sessions.changed`** event (and cron on `cron.changed`) instead of polling.
